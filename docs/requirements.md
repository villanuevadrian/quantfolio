## Project context

QuantFolio is a personal investment portfolio tracking application with a quantitative analysis layer. Designed for a single initial user but architecturally multi-user from day 1.

**Stack:** FastAPI + PostgreSQL + React  
**Deployment:** Local (MVP) → Cloud (Stage 2)

---

## Functional requirements

### Stage 1 — MVP

#### Portfolio management

**RF-01:** The system shall allow the user to create separate portfolios by asset type (stocks, funds, ETFs) to organise their investments.

**RF-02:** The system shall display an aggregated global view of all portfolios so the user can see their total consolidated net worth.

#### Operations

**RF-03:** The system shall allow the user to manually register buy and sell operations, specifying asset, quantity, price and date.

**RF-04:** The system shall allow importing operations from a CSV or Excel file.

#### Tracking

**RF-05:** The system shall calculate and display the current position of each asset: total quantity, average purchase price and current market value.

**RF-06:** The system shall calculate and display the return of each position in absolute value (€) and percentage (%).

**RF-07:** The system shall fetch the current price of assets when the application loads via an external API (Yahoo Finance or similar).

#### Calendar

**RF-08:** The system shall allow the user to manually add events linked to an asset or date (earnings, dividends, personal reminders).

**RF-09:** The system shall automatically sync relevant events for assets in the portfolio (earnings, dividends, splits) via an external API.

---

### Stage 2 — Future features

**RF-10:** The system shall allow configuring price alerts per asset (above / below a threshold).

**RF-11:** The system shall offer AI-assisted portfolio analysis with recommendations based on the user's profile.

**RF-12:** The system shall support crypto assets with real-time prices.

**RF-13:** The system shall be deployed on cloud and support multiple users with isolated data.

## Non-functional requirements

### Performance

**RNF-01:** The system shall respond to any request in under 2 seconds under normal local usage conditions.

### Security

**RNF-02:** Passwords shall be stored hashed (bcrypt). No sensitive data is stored in plain text.

**RNF-03:** Authentication shall be implemented via JWT with configurable expiration.

### Scalability

**RNF-04:** The system shall be designed to support multiple users from the start, even though in the MVP only one user will use it.

**RNF-05:** The code shall be structured in separate layers (router → service → repository) to facilitate maintenance and scalability.

### Portability

**RNF-06:** The system shall be deployed locally via Docker Compose and be ready to migrate to cloud without structural changes.

## Engineering quality requirements

> This section defines code quality standards. Its goal is to make the project representative of professional best practices and suitable for presentation in technical interviews in the fintech / quant sector.

### Testing

**RQ-01:** The project shall include unit tests for the service layer (business logic) with a minimum coverage of 70%.

**RQ-02:** The project shall include integration tests for the main API endpoints (pytest + HTTPX).

**RQ-03:** Every financial calculation function (return, average price, quant metrics) shall have its own test with documented edge cases.

### Quantitative metrics

**RQ-04:** The system shall implement at least the following quant metrics in the service layer:
- Total and period return (daily, monthly, annual)
- Volume-weighted average price (VWAP)
- Historical portfolio volatility
- Sharpe Ratio (with configurable risk-free rate)

> These metrics connect directly to the Quantitative Finance minor and demonstrate technical depth beyond a standard CRUD application.

### Documentation

**RQ-05:** The repository shall include a `README.md` with: project description, architecture, installation and execution instructions, and relevant design decisions.

**RQ-06:** Every API endpoint shall be documented via OpenAPI (auto-generated by FastAPI) with description, parameters and response examples.

**RQ-07:** The code shall include docstrings on all service layer functions and data models.

### Code structure

**RQ-08:** The project shall follow a clear and consistent layered structure:

```
quantfolio/
├── api/          # FastAPI routers (endpoints)
├── services/     # Business logic
├── repositories/ # Database access
├── models/       # SQLAlchemy models
├── schemas/      # Pydantic schemas
└── tests/        # Tests organised by layer
```

**RQ-09:** The project shall use environment variables for all sensitive configuration (credentials, URLs, API keys). No credentials shall appear in source code or git history.

### Version control

**RQ-10:** The repository shall use feature branches (`feature/`, `fix/`) and descriptive commits following Conventional Commits (`feat:`, `fix:`, `docs:`, `test:`).

## Recorded design decisions

| Decision | Alternative considered | Justification |
|---|---|---|
| PostgreSQL | Oracle | Oracle cannot be deployed for free on cloud; PostgreSQL is the fintech standard |
| Holdings calculated at runtime | Materialised table | Smaller bug surface; small data volumes require no optimisation |
| On-demand price fetch on load | Background worker | Simplifies MVP; worker added in Stage 2 for alerts |
| Multi-user design from day 1 | Single-user | Zero cost to add at design time; high cost to refactor later |
| Docker Compose from day 1 | Manual installation | Guarantees reproducibility and simplifies future cloud deployment |
